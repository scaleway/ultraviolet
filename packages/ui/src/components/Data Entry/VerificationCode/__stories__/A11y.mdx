# VerificationCode - Accessibility

## Description

An OTP (one-time password) / verification code input rendered as several separate input boxes (4 by default). Typing auto-advances focus between boxes and full-code paste is spread across the boxes. Supports an optional label and helper/error/success text.

## Summary

1. ❌ **Perceivable**: the component should not be rendered as multiple separate inputs, it should be a single field with the boxes simulated visually. Splitting into several inputs fails WCAG 1.3.1 because the input group is not programmatically named (no `legend`) and the fields do not use `autocomplete="one-time-code"`, breaking OTP autofill. The hardcoded default `aria-label` overrides the visible label, so the visible label's relationship to the field is not conveyed.
2. ✅ **Operable**: fully keyboard operable (auto-advance, Backspace, Arrow keys) with a visible focus indicator.
3. ❌ **Understandable**: uses deprecated `aria-label` pattern; missing `accessibleLabel` prop per RFC #6585. The hardcoded default `aria-label` also makes the announced name differ from the descriptive visible label.
4. ✅ **Robust**: each field has an accessible name, role and value.

## Rules

Enforced by the component:

- ❌ [WCAG 1.3.1 - Info and Relationships (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) - The `<fieldset>` has no `<legend>`, and the label's `htmlFor` points only to the first box, so the group of fields is not programmatically named as a unit.
- ❌ [WCAG 1.3.5 - Identify Input Purpose (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/identify-input-purpose.html) - `autoComplete="off"` prevents browsers from autofilling the code; it should be `autocomplete="one-time-code"`.
- ❌ [WCAG 2.4.6 - Headings and Labels (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html) - default `aria-label`: the announced label is not the descriptive one shown to users
- ✅ [WCAG 2.1.1 - Keyboard (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) - Auto-advance, Backspace, Arrow keys and paste are all keyboard operable.
- ✅ [WCAG 2.4.7 - Focus Visible (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) - A focus box-shadow indicator is applied.
- ✅ [WCAG 3.3.1 - Error Identification (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html) - Error text is displayed and associated via `aria-invalid` / `aria-describedby`.
- ✅ [WCAG 3.3.2 - Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) - A visible label and/or per-field `aria-label` is provided.
- ✅ [WCAG 4.1.2 - Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) - Each field has an accessible name (`aria-label`), an implicit textbox role and a value.
- ✅ [WCAG 4.1.3 - Status Messages (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) - Helper/error/success text is exposed through `role="status"` in `Description`.
- ⚠️ [RFC #6585 - Accessible Icons and Hidden Labels](https://github.com/scaleway/ultraviolet/discussions/6585) - Component uses the deprecated `aria-label` pattern. Should migrate to an `accessibleLabel` prop (hidden label rendered via `VisuallyHidden`) per team standards.

To apply when using the component:

- [WCAG 1.4.1 - Use of Color (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) - Error/success must also be conveyed through text (the `Description`), not only border color, when displayed.
- [WCAG 3.3.3 - Error Suggestion (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/error-suggestion.html) - Provide guidance in the helper about the expected code format (e.g. number of digits) when relevant.

## Accessibility issues

**Critical:**

- **Multiple separate fields instead of a single field.** The recommended accessible OTP pattern is one `<input>` with the boxes simulated visually. The current multi-input approach forces screen reader users to tab through and interpret several "Verification code 0/1/2/3" textboxes, and complicates paste and autofill. If the multi-box design is kept, the fields must be grouped with a `<fieldset>` + `<legend>` and the entire group announced as a single logical unit.

**High:**

- **`autoComplete="off"` blocks OTP autofill**: fails to declare the input purpose, preventing mobile browsers from auto-filling a one-time code. Should be `autocomplete="one-time-code"`.
- **Missing `<legend>` in the `<fieldset>`**: the group of fields has no programmatic name so the group is not announced as a single logical unit.
- **Uses deprecated `aria-label` pattern**: per [RFC #6585](https://github.com/scaleway/ultraviolet/discussions/6585), should migrate to an `accessibleLabel` prop (a hidden label rendered via `VisuallyHidden`) instead of `aria-label`. The current `aria-label` prop should be deprecated in favor of the new pattern.
- **Hardcoded default `aria-label` overrides the visible label**: a default `aria-label` is always applied to every box and takes precedence over the visible `<label>` for the accessible name. The default should be removed so the name comes from the visible label or an explicitly provided `accessibleLabel`.
- **Missing `aria-labelledby`**: the visible `<label>` is only linked to the first box via its `htmlFor`, and is overridden by the always-present `aria-label`. The visible label text is never used as the accessible name, screen readers announce "Verification code 0/1/2/3" instead of the real label, and the remaining boxes have no reference to the visible label at all. Using a single input would help fix this issue.

**Medium:**

- **No `inputmode="numeric"`**: for a numeric code the mobile keypad would be more reliably shown by setting `inputmode="numeric"` (with `type="text"`), as recommended, rather than relying on `type="tel"`.
- **Verbose screen-reader naming**: announcing "Verification code 0", "Verification code 1", ... for each box is noisy; a single labeled field would be clearer.
