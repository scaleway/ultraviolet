# Dialog - Accessibility

## Description

A confirmation/message dialog that presents a short title with a sentiment-based icon and content requiring user interaction. Built on top of `Modal`, it renders a `<dialog>` with focus trap, Escape-to-close, and a set of sub-components (`Button`, `CancelButton`, `Buttons`, `Stack`, `Text`) for composing confirmations.

## Summary

1. ✅ **Perceivable**: Content is text-based; sentiment is conveyed by the title/message, so meaning does not depend on color alone.
2. ⚠️ **Operable**: Keyboard support (Tab, Escape, focus trap) present, but initial focus lands on the `<dialog>` container instead of the least destructive action (Cancel), and focus is not restored for programmatic (non-disclosure) usage.
3. ✅ **Understandable**: Title rendered as a semantic `h2` heading, clear button labels.
4. ❌ **Robust**: Accessible name defaults to the generic `"modal"` instead of the visible title; the visible `h2` title is not linked to the dialog via `aria-labelledby`.

## ARIA Pattern

[Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

## Rules

Enforced by the component:

- ✅ [WCAG 2.1.1 - Keyboard (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) - All interactions (open via disclosure, close, confirm/cancel) are operable via keyboard
- ✅ [WCAG 2.1.2 - No Keyboard Trap (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) - Focus trap via `handleFocusTrap` keeps focus cycling inside while allowing Escape to exit
- ⚠️ [WCAG 2.4.3 - Focus Order (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) - Initial focus on the `<dialog>` element (via `tabIndex={0}`), not the least destructive action; incomplete focus restoration for programmatic modals
- ✅ [WCAG 2.4.6 - Headings and Labels (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html) - Title is a descriptive heading
- ❌ [WCAG 4.1.2 - Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) - Accessible name defaults to generic `"modal"` (`aria-label`) and is not derived from the visible title; no `aria-labelledby` relationship

To apply when using the component:

- [WCAG 1.1.1 - Non-text Content (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html) - The sentiment icon (Check/AlertCircle) is `aria-hidden`; ensure the title or message conveys the meaning
- [WCAG 1.4.1 - Use of Color (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) - Sentiment is conveyed via icon/color; do not rely on color alone, include meaningful text
- [WCAG 1.3.1 - Info and Relationships (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) - Maintain semantic structure (headings, lists) within dialog content
- [WCAG 1.4.3 / 1.4.11 - Contrast (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) - Ensure text and interactive elements inside have sufficient contrast
- [WCAG 2.4.4 - Link Purpose (In Context) (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html) - Use descriptive link text within dialog content
- [WCAG 3.3.2 - Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) - Label any form inputs placed inside the dialog

## Accessibility issues

### Critical

- **Accessible name is the generic `"modal"` instead of the title**: The `<dialog>` gets its name from `aria-label`, which defaults to `'modal'`. The visible `<h2>` title rendered by the `title` prop is not programmatically associated (`aria-labelledby`), so screen reader users hear "modal" rather than e.g. "Discard changes?". The title should drive the accessible name of the dialog.

### High

- **Incorrect initial focus placement**: Focus lands on the `<dialog>` element itself (`tabIndex={0}`) rather than an element inside. For a confirmation dialog, focus should move to the **least destructive action** (e.g. the Cancel button) per the Dialog pattern.

- **No focus restoration for programmatic usage**: When opened with the `open` prop (no `disclosure`), focus is not returned to a logical element on close. Focus should return to the invoking element.

### Medium

- **Visible `title` not associated with the dialog**: The `title` prop renders visible text but it is not wired to the `<dialog>` via `aria-labelledby`. Auto-generate an `id` on the title and reference it so the accessible name matches the visible title, and expose an `ariaLabelledBy` prop for advanced cases referencing an external title.

### Low

- **No `aria-describedby` support**: The description (`Dialog.Text`) is not associated with the dialog; wiring it up would help announce context for simple dialogs.

- **Sentiment icon is decorative only**: The Check/AlertCircle icon is `aria-hidden`; the sentiment is conveyed via color and shape but not announced. Ensure the message text conveys meaning (see 1.4.1).

- **Hardcoded English `aria-label="close"`** (inherited from `Modal`): Not translatable. Per [RFC #6585 - Accessible Icons and Hidden Labels](https://github.com/scaleway/ultraviolet/discussions/6585), prefer `VisuallyHidden` text or an `accessibleLabel` prop over `aria-label` (which is ignored by browser translation and has poorer screen reader support).

## Dependencies

- **Modal component**: Provides the `<dialog>`, focus trap, initial focus, Escape/click-outside handling, close button, and focus restoration behavior — many issues above originate there
- **Button component**: Focus visibility (2.4.7) and contrast (1.4.3) depend on Button implementation
- **Bullet / Icon components**: Sentiment icon is rendered with `aria-hidden`
