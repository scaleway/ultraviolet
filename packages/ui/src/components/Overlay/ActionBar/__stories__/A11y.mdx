# ActionBar - Accessibility

## Description

A floating bar for contextual actions, used by List and Table selection bars. It is rendered through a portal into `document.body`, defaults to `role="dialog"`, and does not manage visibility, focus, or dismissal. It is non-modal: there is no focus trap or `aria-modal`.

## Summary

1. ⚠️ **Perceivable**: Content is text-based and left to consumers; no color-only or contrast issue enforced by the component itself. The fixed `37.5rem` width can overflow a 320 CSS-pixel viewport (WCAG 1.4.10).
2. ⚠️ **Operable**: The component does not trap focus; its children provide the interactions. Portal placement puts the bar at the end of DOM order, which should be checked in context.
3. ✅ **Understandable**: No labels or instructions enforced by the component; consumers provide them for their content.
4. ❌ **Robust**: The default `role="dialog"` has no accessible name, and the component exposes no naming prop. A named `region` or `toolbar` would also need an accessible name.

## ARIA Pattern

There is no single pattern for a generic floating action bar. The [Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) does not describe this non-modal component. For the List/Table selection use case, a named [landmark region](https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/) is a candidate that supports direct navigation without trapping focus. Use the [Toolbar Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) only for a group of at least three related controls that implements its arrow-key and focus-management behavior. Keep `dialog` only if the bar is intentionally treated as a dialog and its naming and focus behavior are defined.

## Rules

Enforced by the component:

- ✅ [WCAG 2.1.2 - No Keyboard Trap (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) - The component does not trap focus; keyboard users can continue to the rest of the page
- ❌ [WCAG 2.4.3 - Focus Order (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) - Portal appends the bar at the end of `document.body`, so its actions come last in the tab order; no focus is moved into the dialog on open or returned to the trigger on dismiss
- ❌ [WCAG 1.4.10 - Reflow (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) - The default fixed width of `37.5rem` can require horizontal scrolling at a 320 CSS-pixel viewport
- ❌ [WCAG 4.1.2 - Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) - The default `role="dialog"` has no accessible name

To apply when using the component:

- [WCAG 2.1.1 - Keyboard (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) - Ensure consumer-provided controls are keyboard operable
- [WCAG 2.4.11 - Focus Not Obscured (Minimum) (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) - Check that the fixed bar does not entirely obscure the page element that retains keyboard focus when the bar appears
- [WCAG 1.3.1 - Info and Relationships (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) - Maintain semantic structure (headings, lists) inside the bar content
- [WCAG 1.4.1 - Use of Color (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) - Ensure meaning is not conveyed by color alone within the bar content
- [WCAG 3.3.2 - Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) - Provide labels for any form controls placed in the bar
- [WCAG 4.1.3 - Status Messages (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) - If the bar communicates a status update (such as a selection count), expose that update as a status message; do not use `status` or `alert` as the role for interactive action controls

## Accessibility issues

**Critical:**

- **Default dialog role has no accessible name**: The component defaults to `role="dialog"` but exposes no `accessibleLabel` or `ariaLabelledBy` prop. A dialog needs an accessible name; without one, screen reader users cannot identify its purpose. Add a naming prop and forward it to the container. A `region` or `toolbar` role also needs an accessible name.

**High:**

- **Role and focus behavior need a product decision**: The default `dialog` role suggests a dialog, but the component has no open/close lifecycle and does not manage focus. Current List/Table selection bars are contextual actions and should remain non-modal so users can move between them and the page. Consider a named `region` for this use case; if retaining `dialog`, define its intended focus behavior and accessible name. A `toolbar` role requires the APG keyboard behavior.

- **Appearance of the bar is never announced (WCAG 4.1.3)**: When the ActionBar is inserted dynamically, nothing announces it, there is no focus move and no live region. The correct mechanism depends on intent: if the bar is an interactive dialog, move focus into it (its accessible name and description then get announced); if it is purely informational/transient, it should use a live-region role rather than `dialog`.

- **Fixed width can fail reflow**: `width: 37.5rem` and horizontal centering can place part of the bar outside a 320 CSS-pixel viewport, requiring two-dimensional scrolling. Add responsive sizing or a max-width that fits the viewport.

**Medium:**

- **Role prop has no matching semantics or validation**: `role` accepts any string, but ActionBar does not provide role-specific labeling or keyboard behavior. Document supported roles and their requirements, or narrow the API to the intended semantic role.
- **Portal order and focus visibility need contextual checks**: The bar is appended at the end of `document.body` and is fixed over page content. Verify keyboard order and that the previously focused page control is not entirely hidden when the bar appears. This is not an automatic WCAG 2.4.3 failure, and a close control or focus capture is not required for a non-modal selection region.
