# ActionBar - Accessibility

## Description

A floating bar that appears at the bottom of the page to display important actions or information. It is rendered through a portal into `document.body` (always on top of other elements) and defaults to `role="dialog"`, behaving as a non-modal dialog: no focus trap, no `aria-modal`, and no built-in close control.

## Summary

1. ✅ **Perceivable**: Content is text-based and left to consumers; no color-only or contrast issue enforced by the component itself.
2. ❌ **Operable**: Portal rendering at the end of `document.body` breaks the logical focus order, no focus is moved into the bar when it appears nor restored on dismissal, and the entrance `fadeIn` animation does not respect `prefers-reduced-motion`.
3. ✅ **Understandable**: No labels or instructions enforced by the component; consumers provide them for their content.
4. ❌ **Robust**: The default `role="dialog"` has no accessible name (no `aria-label`, `aria-labelledby`, or naming prop).

## ARIA Pattern

[Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) - used in its non-modal form: the ActionBar overlays the page but background content remains operable and `aria-modal` is correctly not set.

## Rules

Enforced by the component:

- ✅ [WCAG 2.1.1 - Keyboard (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) - Focusable children remain operable via keyboard; the bar itself does not add non-keyboard interactions
- ✅ [WCAG 2.1.2 - No Keyboard Trap (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) - No focus trap; background content stays reachable with Tab
- ❌ [WCAG 2.4.3 - Focus Order (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) - Portal appends the bar at the end of `document.body`, so its actions come last in the tab order; no focus is moved into the dialog on open or returned to the trigger on dismiss
- ❌ [WCAG 2.3.3 - Animation from Interactions (Level AAA)](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html) - Entrance `fadeIn` animation runs on mount without a `prefers-reduced-motion: reduce` media query
- ❌ [WCAG 4.1.2 - Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) - `role="dialog"` without an accessible name; screen readers announce an unlabeled "dialog"

To apply when using the component:

- [WCAG 1.3.1 - Info and Relationships (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) - Maintain semantic structure (headings, lists) inside the bar content
- [WCAG 1.4.1 - Use of Color (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) - Ensure meaning is not conveyed by color alone within the bar content
- [WCAG 3.3.2 - Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) - Provide labels for any form controls placed in the bar
- [WCAG 4.1.3 - Status Messages (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) - If `role="status"` or `role="alert"` is passed, the bar is only announced when it appears via the live-region semantics of that role

## Accessibility issues

### Critical

- **Dialog role without an accessible name**: The default `role="dialog"` provides no `aria-label` or `aria-labelledby`, and the component exposes no naming prop. Per the Dialog pattern every dialog must have an accessible name. Screen reader users hear an unlabeled "dialog" and cannot identify its purpose. Add an `accessibleLabel`/`accessibleName` prop that is forwarded as the accessible name of the dialog container.

### High

- **No focus management on open/close**: When the bar appears, focus stays where it was and is never moved into the dialog; on dismissal there is no focus restoration to the invoking element. Per the Dialog pattern, focus should move to an element inside the dialog when it opens and return to the trigger (or a logical element) when it closes.

- **Appearance of the bar is never announced (WCAG 4.1.3)**: When the ActionBar is inserted dynamically, nothing announces it, there is no focus move and no live region. The correct mechanism depends on intent: if the bar is an interactive dialog, move focus into it (its accessible name and description then get announced); if it is purely informational/transient, it should use a live-region role rather than `dialog`.

- **Portal breaks focus order (WCAG 2.4.3)**: Rendering via `createPortal(..., document.body)` appends the bar at the very end of the DOM, so keyboard users must tab through the entire page before reaching the bar's actions, even though it is visually at the bottom and contextually near the trigger.

- **Entrance animation ignores reduced motion (WCAG 2.3.3)**: The `fadeIn` animation has no `@media (prefers-reduced-motion: reduce)` guard, unlike `Modal` and `Popup/v2`. Users with vestibular disorders cannot disable the motion.

### Medium

- **Free-form `role` prop**: `role` is an unvalidated string. Passing `alert`/`status` (or a future `aria-modal` toggling) silently changes announcement semantics — `status` and `alert` carry implicit `aria-live` (polite/assertive) and are meant for dynamically inserted content, whereas `dialog` is announced via focus management. The component should document which roles are supported and their requirements, or derive the semantics automatically from usage.

- **No recommended close control**: The Dialog pattern strongly recommends a visible close/cancel button in the tab sequence. The ActionBar has no built-in dismiss; consumers must provide one or manage visibility themselves, so documentation should call this out.

### Low

- **Reconsider the default `role="dialog"`**: A purely informational or transient floating bar is better served by a live-region role (`status`/`alert`) or a `region`/`toolbar`, which do not require an accessible name or focus management the way a dialog does. Aligning the default role with the actual semantics would resolve both the naming (4.1.2) and announcement (4.1.3) issues for informational usage.
