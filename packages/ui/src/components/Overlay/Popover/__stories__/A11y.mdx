# Popover - Accessibility

## Description

A non-modal overlay dialog that displays additional information or actions on top of the main content when triggered. It includes a title, a close button and a content area, and is usually triggered by clicking a button.

## Summary

1. ✅ **Perceivable**: the dialog is named by its visible title through `aria-labelledby`, and decorative icons are hidden from assistive technology.
2. ✅ **Operable**: focus moves into the dialog on open, is trapped while open and returns to the trigger on close (Escape or close button).
3. ✅ **Understandable**: content and close affordance are predictable and readable.
4. ✅ **Robust**: the `dialog` role is named (`aria-labelledby`), and the trigger exposes `aria-haspopup="dialog"` / `aria-expanded` / `aria-controls`.

## ARIA Pattern

[ARIA Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

The Popover maps to the Dialog pattern. As a non-modal dialog it correctly does not set `aria-modal="true"`, but it still provides an accessible name and manages focus. Naming conventions follow [RFC #6585 - Accessible Icons and Hidden Labels](https://github.com/scaleway/ultraviolet/discussions/6585): prefer `aria-labelledby` referencing visible text over `aria-label`, and avoid hardcoded, non-localizable labels.

## Rules

Enforced by the component:

- ✅ [WCAG 4.1.2 - Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) - `role="dialog"` is set and the dialog is named by its visible title via `aria-labelledby` (generated `id` on the `<h2>`), per RFC #6585.
- ✅ [WCAG 1.3.1 - Info and Relationships (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) - the title (`<h2>`) is programmatically associated with the dialog container through `aria-labelledby`.
- ✅ [WCAG 2.4.3 - Focus Order (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) - focus moves into the dialog on open and returns to the trigger on close (Escape or close button).
- ✅ [WCAG 2.1.1 - Keyboard (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) - the dialog can be opened from a focusable trigger and closed with the Escape key and the close button.
- ✅ [WCAG 2.1.2 - No Keyboard Trap (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) - Escape provides a way out of the dialog.
- ✅ [WCAG 2.4.7 - Focus Visible (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) - the close button keeps a visible focus indicator.
- ✅ [WCAG 1.1.1 - Non-text Content (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html) - the decorative `CloseIcon` is hidden with `aria-hidden="true"` (default of the `Icon` component when no `accessibleLabel` is provided).
- ⚠️ [WCAG 1.4.13 - Content on Hover or Focus (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html) - the Popover is dismissible via Escape and a close button; hoverable and persistent behavior depends on usage.

To apply when using the component:

- [WCAG 1.4.1 - Use of Color (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) - the `primary` sentiment conveys meaning through color; ensure the sentiment is also conveyed through text (title/content).
- [WCAG 1.4.3 - Contrast (Minimum) (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) - ensure text on `primary` background meets contrast requirements.

<summary>Past accessibility issues</summary>

**Critical:**

- ✅ Dialog has no accessible name.
  - The popup rendered `role="dialog"` without `aria-labelledby` (the title had no `id` to reference) or an `aria-label`, so screen readers announced an unnamed dialog (WCAG 4.1.2 / 1.3.1).
  - **Resolved** by generating an `id` with `useId()` in `index.tsx`, attaching it to the visible `<h2>` title (`ContentWrapper.tsx`) and referencing it with `aria-labelledby` on the panel (per RFC #6585, referencing visible text rather than `aria-label`).

**High:**

- ✅ No focus management on open.
  - Focus remained on the trigger instead of moving into the dialog, contrary to the Dialog pattern (WCAG 2.4.3).
  - **Resolved** by enabling `focusTrap` on the popup panel: `FloatingFocusManager` now moves focus to the first focusable element (the close button) when the dialog opens.

- ✅ No focus restoration on close.
  - When dismissed (close button or Escape), focus was not returned to the triggering element and was lost to the document (WCAG 2.4.3).
  - **Resolved** by `FloatingFocusManager`'s `returnFocus` (default `true` on `Popup.Panel`), which returns focus to the trigger on close.

**Medium:**

- ✅ Trigger did not expose `aria-haspopup="dialog"`.
  - Assistive technologies were not told that activating the trigger opens a dialog.
  - **Resolved** in `Popup.Trigger`: `aria-haspopup`, `aria-expanded` and `aria-controls` are now set on the trigger's focusable element, with `aria-haspopup` derived from the panel role.

- ⚠️ Close button uses a generic accessible name.
  - The close button is labelled with the generic, non-localizable text "close" (`ContentWrapper.tsx`) and does not tell screen reader users which popover they are closing (WCAG 2.5.3 / 4.1.2).
  - The label is provided through `accessibleLabel`, rendered as visually hidden text (RFC #6585) rather than `aria-label`, matching the `Modal` convention, but it remains the generic "close". Making it descriptive (e.g. "Close \{title\}") requires an i18n mechanism not available to the component.

**Low:**

- ✅ The `CloseIcon` inside the close button was not `aria-hidden`.
  - The decorative icon was exposed to assistive technology (WCAG 1.1.1).
  - **Resolved** by the `Icon` component, which now defaults to `aria-hidden="true"` for decorative icons (no `accessibleLabel`).

- ⚠️ Focus trap on a non-modal dialog.
  - The popover is non-modal yet traps Tab focus inside the panel (`focusTrap`), which is semantically inconsistent with non-modal behaviour (WCAG 2.1.2). Escape remains the way out.
  - Kept intentionally so focus stays within the dialog while it is open; revisit if a non-trapping, non-modal behaviour is required.

- ⚠️ The native `<dialog>` element could be used.
  - The popup is a `div` with `role="dialog"` rather than a native `<dialog>` element. Not required for WCAG conformance; noted as a possible improvement.
