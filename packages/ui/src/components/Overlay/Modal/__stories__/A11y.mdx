# Modal - Accessibility

## Description

Modal is a dialog component that displays content on top of other page content, commonly used for dialogs with additional information or confirmations. It moves focus inside on open, traps it, restores it on close, and supports keyboard navigation (Escape to close), accessible naming (`ariaLabelledBy` / `accessibleLabel`) and description (`ariaDescribedBy`).

## Summary

1. ✅ **Perceivable**: Semantic `<dialog>` element, accessible naming via `ariaLabelledBy` or `accessibleLabel`, labelled close button, `imageAlt` for images.
2. ✅ **Operable**: Focus moves to the first focusable element inside the dialog on open, the focus trap keeps Tab cycles inside, and focus is restored to the previously focused element on close — including modals opened with the `open` prop.
3. ✅ **Understandable**: Clear labeling via `ariaLabelledBy`/`accessibleLabel`, consistent behavior.
4. ✅ **Robust**: `ariaLabelledBy` and `ariaDescribedBy` are forwarded to the native `<dialog>`. Native `showModal()` is intentionally not used (top-layer conflicts with popups) and `preventBodyScroll` is kept for `Drawer`'s push variant.

[Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

## Rules

Enforced by the component:

- ✅ [WCAG 2.1.2 - No Keyboard Trap (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) - Focus trap via `handleFocusTrap`
- ✅ [WCAG 2.4.3 - Focus Order (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) - Initial focus goes to the first focusable element inside the dialog; focus is restored to the previously focused element on close, with or without a `disclosure`
- ✅ [WCAG 4.1.2 - Name, Role, Value (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) - `ariaLabelledBy` or `accessibleLabel`, plus `ariaDescribedBy`

To apply when using the component:

- [WCAG 1.3.1 - Info and Relationships (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) - Ensure semantic structure (headings, lists) within modal content
- [WCAG 1.4.11 - Non-text Contrast (Level AA)](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) - Ensure 3:1 contrast for interactive elements within modal
- [WCAG 2.4.4 - Link Purpose (In Context) (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html) - Ensure descriptive link text within modal
- [WCAG 3.3.2 - Labels or Instructions (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) - Provide labels for form inputs within modal
- [WCAG 2.1.2 - No Keyboard Trap (Level A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) - Avoid combining `hideOnEsc={false}`, `isClosable={false}`, and `hideOnClickOutside={false}` without providing a manual close button in the modal content

## Past accessibility issues

<details>
<summary>Resolved and remaining issues</summary>

### Medium

- ✅ Incorrect initial focus placement:
  - Focus landed on the `<dialog>` element itself instead of an element **inside** the dialog: screen reader users heard container focus instead of meaningful content.
  - **Resolved** by focusing the first focusable element inside the dialog on open, and falling back to the dialog itself when it contains none (`components/Dialog.tsx`).
- ✅ Missing `heading` prop and `aria-labelledby`:
  - Only `ariaLabel` was supported, not `aria-labelledby` for visible titles.
  - **Resolved** with the `ariaLabelledBy` and `ariaDescribedBy` props, forwarded to the `<dialog>`. A `heading` prop was not added to keep the visible title under the consumer's control.
- ⚠️ `preventBodyScroll` prop is problematic:
  - A real modal should always prevent background scrolling.
  - **Kept** as-is: removing it is a breaking API change and `Drawer`'s `push` variant relies on `preventBodyScroll={false}`. It still defaults to `true`.
- ⚠️ Not using native `<dialog>` methods:
  - `showModal()`/`close()` would provide built-in focus management and Escape handling, but `showModal()` promotes the dialog to the top layer, above portalled `SelectInput`/`Popup` panels.
  - **Kept** as-is: adopting native methods requires reviewing every component with popups first.
- ✅ No focus restoration for programmatic modals:
  - When using `open` without `disclosure`, focus was not restored on close.
  - **Resolved** by capturing `document.activeElement` on open and restoring it on close and unmount (`components/Dialog.tsx`).

### Low

- ✅ No `aria-describedby` support:
  - **Resolved** with the `ariaDescribedBy` prop.
- ✅ Image alt text is generic:
  - `alt="illustration"` was not descriptive.
  - **Resolved** with the `imageAlt` prop, defaulting to `''` (decorative image).
- ⚠️ Hardcoded English `aria-label="close"`:
  - Close button label is not translatable. Needs a global translatable-labels solution (see the [Accessible Icons and Hidden Labels](https://github.com/scaleway/ultraviolet/discussions/6585) RFC); a component-level prop was deliberately not added.
- ✅ No `ariaLabelledBy` prop:
  - **Resolved** with the `ariaLabelledBy` prop (see above).

</details>

## Dependencies

- **Button component**: Focus visibility (WCAG 2.4.7) and contrast (WCAG 1.4.3) depend on Button implementation
- **Dialog component**: Underlying implementation affects accessibility semantics
